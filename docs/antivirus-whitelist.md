# 杀软误报申报

规范：`openspec/changes/add-steadcopy-release/specs/build-release/spec.md` → Requirement: 发布门控（R14）

## 为什么会误报

稳拷有几个行为，在启发式引擎眼里长得和勒索软件很像：

| 我们做的事 | 引擎看到的 |
|---|---|
| 遍历整张卡、读取全部文件 | 大范围文件枚举与读取 |
| 同时向多个目录高速写入 | 大批量文件创建 |
| `FILE_FLAG_NO_BUFFERING` 直接读设备 | 绕过文件系统缓存的原始访问 |
| `FSCTL_LOCK_VOLUME` / `FSCTL_DISMOUNT_VOLUME` | 卷级独占操作 |
| 快速格式化（`fmifs.dll` 的 `FormatEx`） | 破坏性磁盘操作 |
| NSIS 打包 + 未签名 | 低信誉安装器 |

加上**没有代码签名证书**，SmartScreen 与多数引擎都会给一个「未知发布者 / 低信誉」的判定。这是预期结果，不是 bug。

## 我们不做什么

**不在任何文档、安装界面、应用内提示中建议用户关闭安全软件。** 让用户为了跑我们的程序而降低整机防护，是把成本转嫁给用户去换我们自己的安装成功率。

这条有机检兜底：`scenario_build_release_docs_never_tell_users_to_disable_protection` 会扫描 README 与全部 `docs/*.md`。

也**不做**这些：

- 不用加壳、混淆、反调试——它们只会让信誉分更低，还让误报申报变得没法解释
- 不在安装器里替用户改 Defender 排除项
- 不建议用户用「以管理员身份运行」绕过提示

## 发版前要做的

### 1. 先自测一遍

拿本次的安装包与便携版，在干净机器上跑：

```bash
python scripts/build-release.py
```

然后把 `release/` 下的产物上传 VirusTotal，记录检出率与检出引擎名单。**多引擎检出时先自查**：是不是打包链路里混进了什么（比如 UPX、第三方 sidecar）。

### 2. 申报表要素

每家的表单大同小异，准备好这几项，一次填完：

- 产物文件与 SHA-256（取自 `release/SHA256SUMS.txt`）
- 项目主页与源码仓库地址（**开源是最有力的材料**——引擎方能自己编译比对）
- 产物是什么、为什么会触发启发式（把上面那张表贴过去）
- 联系邮箱

### 3. 申报入口

| 厂商 | 入口 | 备注 |
|---|---|---|
| Microsoft Defender | Microsoft Security Intelligence 的样本提交页，选「Software developer」 | 中文用户覆盖面最大的一家，优先 |
| 火绒 | 官网「误报反馈」 | 国内用户占比高 |
| 360 | 官网「误拦截申诉」 | 同上 |
| 腾讯电脑管家 | 官网「误报提交」 | 同上 |
| Avast / AVG | 同一个 false-positive 表单 | 引擎共用 |
| Kaspersky / ESET / Bitdefender | 各家 false-positive 表单 | 海外用户 |

### 4. 记录回执

在 `release/gate-<版本>.md` 的 R14 一项里记：申报日期、厂商、单号、回执结论、复检日期。

**没有回执不等于申报失败**——多数厂商只在处理完成后更新特征库，不一定回信。复检方式是过几天重新上传 VirusTotal 看该引擎是否已放行。

## 长期的解法

误报申报是每个版本都要重来一次的体力活。真正的解法是**代码签名证书**（决策 P7 里主理人选择「先靠官网校验码过渡」）：

- OV 证书：便宜，但 SmartScreen 信誉要靠下载量慢慢攒
- EV 证书：贵，且需要硬件密钥，但 SmartScreen 信誉是即时的

在没有证书之前，`docs/verify-download.md` 的校验码核对就是用户确认来源的唯一手段，它必须在下载页显著位置。

## 用户侧的正确做法

如果用户问「杀毒软件拦了怎么办」，回答是：

1. 先核对 SHA-256 校验码，确认下载到的确实是我们发布的文件
2. 校验码对得上，就在安全软件里**针对这一个程序**添加信任
3. 校验码对不上，**不要运行**，去官网重新下载

不要建议关闭防护、不要建议卸载安全软件、不要建议关闭实时保护。
